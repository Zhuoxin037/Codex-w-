## 确定问题详单

### F01 · P1 · 正常在线玩家每秒都会重新走加入流程

**范围：**manacore，所有在线玩家。

**源码：**[manacore-1.0.0/data/manacore/function/core/second.mcfunction:24](D:/数据包/manacore-1.0.0/data/manacore/function/core/second.mcfunction:24)；[manacore-1.0.0/data/manacore/function/internal/session/tick_self.mcfunction:18](D:/数据包/manacore-1.0.0/data/manacore/function/internal/session/tick_self.mcfunction:18)；[manacore-1.0.0/data/manacore/function/internal/join/slot_check.mcfunction:25](D:/数据包/manacore-1.0.0/data/manacore/function/internal/join/slot_check.mcfunction:25)；[manacore-1.0.0/data/manacore/function/internal/join/register.mcfunction:21](D:/数据包/manacore-1.0.0/data/manacore/function/internal/join/register.mcfunction:21)

**问题与影响：**`#sec` 先加 1，再判断玩家旧心跳是否大于等于新秒数。正常在线玩家的心跳比新秒数小 1，因此每秒触发 join，扫描 UUID 索引并再次派发 player_join。当前威霆加入回调还会执行清理与重建。这里不能把每秒事件当成真正上线事件，人数增加时也会产生额外扫描。

**复现/路径推演：**单玩家持续在线，在 player_join 标签末尾临时加入计数回调，等待 10 秒；按当前路径会收到约 10 次事件，而非只在加入时收到 1 次。

**建议：**用“上一秒正常心跳”与“首次上线/断线重连/加载代际变化”分开判断。已有有效 slot 的玩家直接更新心跳，不要重新注册和发 join。

### F02 · P1 · 回收池仅剩一个槽位时，会连续执行两次分配

**范围：**manacore，重连/新玩家分配。

**源码：**[manacore-1.0.0/data/manacore/function/internal/slot/alloc.mcfunction:9](D:/数据包/manacore-1.0.0/data/manacore/function/internal/slot/alloc.mcfunction:9)；[manacore-1.0.0/data/manacore/function/internal/slot/from_free.mcfunction:8](D:/数据包/manacore-1.0.0/data/manacore/function/internal/slot/from_free.mcfunction:8)

**问题与影响：**alloc 的两个条件顺序执行。from_free 弹出最后一个元素后，第二条 unless 判断变为真，马上再执行 new，覆盖刚取得的槽位。最后一个回收槽位因此被丢弃，next_slot 提前增长，加速触发溢出。

**复现/路径推演：**free_slots.list=[5]、next_slot=10：期望分配 5；当前路径先取 5，再分配 11，最终拿到 11，5 从池中消失。

**建议：**把分配做成互斥分支，例如命中回收分支后直接 return run function from_free，或先保存分支条件再执行。

### F03 · P1 · UUID 查找遗漏最后一个合法槽位

**范围：**manacore，默认第 64 个槽位。

**源码：**[manacore-1.0.0/data/manacore/function/internal/join/slot_check.mcfunction:14](D:/数据包/manacore-1.0.0/data/manacore/function/internal/join/slot_check.mcfunction:14)；[manacore-1.0.0/data/manacore/function/internal/index/find_uuid_loop.mcfunction:10](D:/数据包/manacore-1.0.0/data/manacore/function/internal/index/find_uuid_loop.mcfunction:10)；[manacore-1.0.0/data/manacore/function/internal/slot/new.mcfunction:10](D:/数据包/manacore-1.0.0/data/manacore/function/internal/slot/new.mcfunction:10)

**问题与影响：**分配槽位是 1..max_slots，但查找从 0 开始，并在 i>=max_slots 时退出，只查到 0..63。默认 slot=64 的记录永远找不到；与 F01 叠加时会反复补发槽位，留下旧索引并快速触发 F04。

**复现/路径推演：**在 index."64" 放入某玩家 UUID，令 max_slots=64，调用加入查找；该 UUID 不会被命中。

**建议：**查找统一为 1..max_slots，包括上界；同时统一所有 foreach、分配和校验的编号约定。

### F04 · P1 · 槽位耗尽后回绕到 1，直接覆盖正在使用的索引

**范围：**manacore，超过容量或槽位泄漏后。

**源码：**[manacore-1.0.0/data/manacore/function/internal/slot/new.mcfunction:11](D:/数据包/manacore-1.0.0/data/manacore/function/internal/slot/new.mcfunction:11)；[manacore-1.0.0/data/manacore/function/internal/slot/overflow.mcfunction:9](D:/数据包/manacore-1.0.0/data/manacore/function/internal/slot/overflow.mcfunction:9)；[manacore-1.0.0/data/manacore/function/internal/join/register.mcfunction:14](D:/数据包/manacore-1.0.0/data/manacore/function/internal/join/register.mcfunction:14)

**问题与影响：**overflow 把 next_slot 重置为 1，register 随后无条件重写 index."1"。旧玩家仍持有 slot=1，两人索引归属冲突；self_uuid、心跳、离线扫除以及后续 mana API 都可能作用到错误记录。回绕还让 foreach 的遍历上界缩小，高位索引无法正常维护。

**复现/路径推演：**默认 max_slots=64，在所有槽位占用时分配第 65 次；index."1" 的 UUID 会被新玩家覆盖。F02/F03 可使较少玩家也提前到达该路径。

**建议：**容量耗尽时明确拒绝注册并返回 slot_full，或安全扩容；只能复用已经确认空闲的槽位，禁止绕回覆盖。

### F05 · P1 · self_uuid 查询失败时会返回上一次调用留下的 UUID

**范围：**manacore API，未注册/失效槽位玩家。

**源码：**[manacore-1.0.0/data/manacore/function/api/player/self_uuid.mcfunction:20](D:/数据包/manacore-1.0.0/data/manacore/function/api/player/self_uuid.mcfunction:20)；[manacore-1.0.0/data/manacore/function/internal/debug/self_uuid.mcfunction:7](D:/数据包/manacore-1.0.0/data/manacore/function/internal/debug/self_uuid.mcfunction:7)；[sweetdream/data/sweetdream/function/lib/uuid.mcfunction:19](D:/数据包/sweetdream/data/sweetdream/function/lib/uuid.mcfunction:19)

**问题与影响：**self_uuid 不先清空 work.a.uuid。索引不存在时，debug/self_uuid 的条件写入被跳过，旧 uuid 仍存在，外层便当成成功结果返回。sweetdream 的 lib/uuid 会将非空结果标为有效；首次注册前、reload 窗口或索引异常时可能串用别人的 UUID。

**复现/路径推演：**先让玩家 A 成功读取 self_uuid，再让没有有效 index 的玩家 B 调用；work.a.uuid 可仍是 A 的 UUID。

**建议：**每次调用先清空查询结果；读取前验证 slot 及 UUID 归属。缺索引必须返回空结果和明确失败原因。

### F06 · P1 · skill/cast 的 mana 参数没有传给实际扣费函数

**范围：**manacore 一步施法 API；应用层多数技能走另一条分步路径。

**源码：**[manacore-1.0.0/data/manacore/function/api/skill/cast.mcfunction:37](D:/数据包/manacore-1.0.0/data/manacore/function/api/skill/cast.mcfunction:37)；[manacore-1.0.0/data/manacore/function/internal/skill/stage_mana.mcfunction:9](D:/数据包/manacore-1.0.0/data/manacore/function/internal/skill/stage_mana.mcfunction:9)；[manacore-1.0.0/data/manacore/function/internal/mana/consume.mcfunction:21](D:/数据包/manacore-1.0.0/data/manacore/function/internal/mana/consume.mcfunction:21)

**问题与影响：**cast 的入参字段是 mana，stage_mana 直接调用内部 consume，而 consume 读取的是 a.value，途中没有转换。标准 cast 调用不能按 mana 正确扣费；缺失字段的 execute store 结果会落为 0。不能据此推断 sweetdream 的全部技能都免魔，因为多数技能另行调用 mana/consume 并传 value。

**复现/路径推演：**按文档使用 {uuid:有效UUID,skill:"audit:test",mana:20.0,consume:1b} 调用 cast，并比较前后 current_mana；当前链路不会按 20 正常扣费。

**建议：**在 stage_mana 建立独立扣费参数，将 mana 映射为 value，再恢复施法上下文。增加成功扣费、魔力不足、consume=0 三种引擎回归场景。

### F07 · P1 · 伤害事件调用其他 API 后，会破坏外层 deal/cast 的参数

## 建议处理顺序与验收场景

1. **先稳定前置状态：**F01–F05。验收首次加入、持续在线、离线重连、reload、单元素回收池、第 64 槽位和满容量；同一 UUID 只应占一个有效 slot，任何分配都不能覆盖其他玩家。
2. **稳定 API：**F06/F07/F15/F19。验收扣费正确、参数非法返回失败、嵌套调用保留上下文；穿共振调用 deal/cast 后伤害能实际落地。
3. **稳定伤害与多人技能：**F08/F09/F10/F11/F13/F14/F17。至少两名玩家，同一组与不同组目标并行；目标遍历顺序不改变每个目标伤害，第二次失败施法不取消第一轮攻击，回手不丢物品。
4. **修功能和工作流：**F12/F16/F18/F20/F21。尤其把部署源切到完整版，再做一轮游戏 reload 与代表外观检查。
5. **发布前验收：**处理 C01/C02 的配置，执行 R01–R06；再按 O01–O10 做性能、体积与维护改进。性能记录至少包含版本、人数、实体量、活动技能、MSPT、客户端 FPS 和资源重载耗时。
